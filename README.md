# Event Photographic Records

A generic EarthRanger workflow that downloads the **photos attached to events** (image attachments only; PDFs, audio etc. are skipped) for a chosen period and turns them into a **photographic records annex**, one row per photo. Partners can attach it to the reports they submit, e.g. ICMBio's *Anexo – Registro Fotográfico*. It produces an interactive dashboard and a Word (`.docx`) report.

Nothing in it is partner-specific. You choose which events to include (time range, event types, event states), and optionally **group** them into separate views, each with its own report. Labels come in English, Portuguese or Spanish. Branding is set through parameters: organization, title, logo and intro text.

## Grouping

**Group by** uses the standard ecoscope groupers:

| Group by | Result |
|---|---|
| Nothing (default) | One view and one report. All records form a single sequence, ordered by event time: oldest first or newest first (**Oldest First**). |
| **Event Type** or **Event Category** | One dashboard view per type or category. Each view has its own stat cards, table and report. |
| A **time** grouper (the core options: Year, Month, Year and Month, Day of the week, …) | One view per period, based on event time |
| A combination, e.g. Event Type + Month | One view per combination, e.g. "Caça · Junho" |

Each view's report restarts at Record 01 / Figure 1. Its cover subtitle carries the group, e.g. "Caça · Junho · 1 de maio de 2026 – 30 de junho de 2026". Month and weekday names follow the report language; the platform itself always produces them in English.

When a grouper is set but the period has no records, there's nothing to split, so the run produces no views and no report. Without a grouper, an empty selection still produces a report with a "no records" note.

## Dashboard

| Widget | Shows |
|---|---|
| Photos | Number of photos in the annex |
| Events with Photos | Number of events that have at least one photo |
| Photographic Records | One row per photo. **Information**: record number, event ID, date and time, classification (Category › Type), coordinates (decimal and DMS), and optionally the event details. **Image**: thumbnail, figure number, file name. Photos of the same event share one Information cell. |

## Report (.docx)

Modelled on ICMBio's *Anexo Fotográfico SMART*:

- **Cover page**: optional logo, organization, title, reporting period, intro paragraph, and the number of records and photos. If nothing matches the filters, it says so.
- **One record per event**, each on a new page:
  - heading (`Record 03 – Hunting`);
  - info table: Event ID, Date and time, Classification, Coordinates, and optionally Details;
  - the photos, two per row, each captioned `Figure N. Photographic record of event …`. Figure numbers run on across the whole annex.

Photos are rotated using their EXIF orientation and downscaled before embedding, so the file stays a size you can email. The layout lives in `resources/templates/photo_records_annex_template.docx`, a [docxtpl](https://docxtpl.readthedocs.io/) template generated by `scripts/build_photo_records_template.py`. To restyle it, edit the script and rebuild, or point the **Template** parameter at your own `.docx` that uses the same context keys (listed in the script's docstring).

Also written to the results folder:
- `<hash>_<file name>[_<group>].docx`: one report per view, e.g. `d71d26_photo_records_annex.docx` or `1b5bd8_photo_records_annex_Caça_Junho.docx`;
- `photo_records.csv`: one row per photo, covering all views;
- `attachments/<event_id>/NN_<filename>`: the downloaded photos.

### Files tab (ecoscope desktop)

`<hash>` is the first 6 hex characters of `sha256` of the view's key, e.g. `{"event_type": "Caça"}`. With no grouper the key is `{"All": "True"}` → `d71d26`. This is the same convention APN and Eden use, and the desktop app strips the prefix from the displayed name.

Since ecoscope-desktop `3bb4587d`, a file appears in a run's **Files** tab only if it is declared in `result.json`; the old file-name-only rule covered just `.csv`/`.parquet` files. So each report is also declared on its own view, and the CSV on every view: `create_files_single_view` → `gather_dashboard(files=...)`.

## Parameters

In form order:

| Group | Parameter | Notes |
|---|---|---|
| | Data Source | EarthRanger connection |
| | Time Range | Reporting period. Event times are shown in its timezone. |
| | Group by | Optional. Event Type, Event Category and/or a time grouper (see [Grouping](#grouping)). |
| Event Selection | Event Types | Leave empty for all types |
| | Event States | Leave empty for all states |
| Photos | Photo Size | Original, Extra large (1920 px, default) or Large (800 px). See below. |
| | Parallel Downloads (advanced) | Default 8 |
| | Thumbnail Size (advanced) | Dashboard table thumbnails: default 480 px, range 200–1024. Larger looks sharper but makes the table HTML bigger. |
| Report Settings | Language | English / Português / Español. Applies to text the workflow writes itself: headings, field labels, captions, date format, the default title and intro, and the dashboard table labels. Names and values that come from EarthRanger (event types, categories, form fields) stay as they are in ER. |
| | Report Title, Introduction | Default to English text ("Photographic Records Annex" and a standard intro). Replace them when you pick Português or Español. Introduction is a text box. |
| | Organization, Subtitle, Logo | Optional. A blank subtitle shows the group (if any) and the reporting period. |
| | Oldest First | On: earliest event is Record 01. Off: latest event is Record 01, as in the ICMBio reference. |
| | Include Event Details | Adds a "Details" row listing the filled-in event form fields |
| | File Name, Template (advanced) | Output file name, and the .docx template (defaults to this repo's) |

Only image attachments are downloaded, and all of them are included.

## How it works

```
get_events (time range, event types, states, with details)
  → convert_values_to_timezone → get_event_type_display_names_from_events
  → add_event_category_display → process_events_details (field titles, choice labels)
  → download_event_photos            attachments/<event_id>/01_<name>, 02_<name>, …
  → build_photo_records              one row per readable image, sorted, numbered → photo_records.csv
  → add_temporal_index → split_groups (groupers; AllGrouper when none)
  → renumber_photo_records           per view: restart at Record 01 / Figure 1
      ├─ dataframe_count / nunique → stat widgets          ─┐
      ├─ format_photo_records_table → persist_text → table ─┤ merge_widget_views
      └─ generate_photo_records_report → <hash>_….docx      │
           → create_files_single_view (per view) ───────────┴→ gather_dashboard(groupers, files)
```

The new tasks are in [`ecoscope-workflows-ext-wd`](../wd-partner-tasks/src/ecoscope-workflows-ext-wd): `tasks/_photo_records.py`, plus `set_int_var` in `tasks/_vars.py`, since the core platform has only bool, float and string variables.

`download_event_photos` is used instead of ext-custom's `download_event_attachments` because ER doesn't keep attachment names unique within an event. With the original names, a second `image.jpg` overwrites the first, so one photo is lost and the other appears twice. This happened 6 times in Iguaçu's May–June 2026 data. Prefixing each file with its upload order avoids it.

Downloads run in parallel (8 at a time by default). By default each photo is downloaded as EarthRanger's server-side `xlarge` copy, which fits within 1920 px, rather than the original. The size names come from er-server's `VERSATILEIMAGEFIELD_RENDITION_KEY_SETS`, and they are requested as `.../file/<id>/<size>/<name>`. On Iguaçu's May–June 2026 hunting photos (78 files, measured in one run):

| Size | Downloaded | Time |
|---|---|---|
| `original` | 121.9 MB | 136 s |
| `xlarge` | 44.2 MB | 84 s |
| `large` | 10.1 MB | 25 s |

The report scales photos to 1024 px, so `xlarge` looks the same as `original`. ER applies EXIF rotation when it resizes, and all 11 rotated phone photos in that set came out the right way up. ER's own web app uses `original`, so pick that size when you need the untouched files.

An empty selection (no events, or no photos) is a normal outcome. Without a grouper, the table and report still render, with a "no records" note.

## Verified against ICMBio

`param.yaml` reproduces the period of ICMBio's hand-made *Anexo Fotográfico SMART*: `parnaiguacu`, Caça (`caceria`), May–June 2026, Portuguese, newest first. The workflow finds 42 events with 78 photos. The reference, which was curated by hand, has 34 records and 43 photos. Event times and coordinates match the reference: for example, its *Registro 02* (`24/06/2026 13:57`, `25°29'57.46"S / 54°09'07.64"W`) is ER event 2432. The reference's classification has a third level taken from SMART (e.g. "Petrechos, armadilhas e estruturas"). ER doesn't have that level, so the closest equivalent here is the event form fields shown under Details (e.g. "Estruturas observadas: Saleiro").

## Local development

```bash
make compile      # build ext-wd into the local channel, compile spec.yaml, install the env
make recompile    # same, updating an existing env
make run          # run with param.yaml against real data (results in OUTPUT_DIR)
make open         # open the HTML outputs
```

Override `PARAM_FILE`, `OUTPUT_DIR`, etc. in `Makefile.local`.

To rebuild the template:

```bash
pixi run --manifest-path ../wd-partner-tasks/src/ecoscope-workflows-ext-wd/pyproject.toml \
    -e test-py312 python scripts/build_photo_records_template.py
```

### Releasing

`spec.yaml` pins the published `ecoscope-workflows-ext-wd` (`0.0.5`, from `https://repo.prefix.dev/ecoscope-workflows-custom/`). To test unreleased ext-wd changes, point that requirement at the local build channel `file:///tmp/ecoscope-workflows-custom/release/artifacts/` and use `make recompile`; that target builds ext-wd from `../wd-partner-tasks` first. Then tag a new `wd-v*`, switch back to the published channel at that version, and recompile.
